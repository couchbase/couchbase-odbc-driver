# Running the libcouchbase connection tests

These standalone programs (`0.*`–`6.*`) exercise libcouchbase directly — the same
library the ODBC driver uses internally — to reproduce and verify connection /
service-discovery behaviour against a Couchbase cluster or Operational Insights (OI).

> **Important:** build and link against the **bundled** `contrib/libcouchbase-odbc`,
> *not* the system/homebrew `libcouchbase`. Homebrew ships stock 3.3.x, which lacks
> fixes carried in this repo's submodule (e.g. CCBC-1682 "Fix Analytics discovery",
> which changes the bucketless HTTP bootstrap endpoint to
> `/pools/default/nodeServicesStreaming/`). Linking homebrew's lib will silently
> reproduce old bugs — analytics `NOT FOUND`, `LCB_ERR_UNSUPPORTED_OPERATION (214)`.

---

## 1. Build the bundled libcouchbase (once)

Out-of-source build, with tests/tools/examples off to keep it fast:

```bash
cd ../../contrib/libcouchbase-odbc      # from this dev/ folder; or use the abs path below

cmake -S . -B build -DCMAKE_BUILD_TYPE=Release \
  -DLCB_NO_TESTS=ON -DLCB_NO_TOOLS=ON -DLCB_NO_MOCK=ON -DLCB_BUILD_EXAMPLES=OFF \
  -DOPENSSL_ROOT_DIR=/opt/homebrew/opt/openssl@3

cmake --build build --target couchbase -j4
```

Produces `contrib/libcouchbase-odbc/build/lib/libcouchbase.2.dylib`.

Sanity-check the fix is in the binary:

```bash
strings build/lib/libcouchbase.2.dylib | grep -i nodeServicesStreaming
# -> /pools/default/nodeServicesStreaming/   (and NO /poolsStreaming/default/)
```

## 2. Compile a test against the bundled lib

Run from this folder (`dev/basic_connection_via_libcouchbase`). Example uses
`0.connect_to_analytics_without_ssl.cpp` — swap the filename for any other test.

```bash
LCB=/Users/janhavi.tripurwar/Documents/BH/couchbase-odbc-driver/contrib/libcouchbase-odbc

g++ -std=c++17 0.connect_to_analytics_without_ssl.cpp -o prog_fixed \
  -I"$LCB/include" \
  -I"$LCB/build/generated" \
  -L"$LCB/build/lib" \
  -Wl,-rpath,"$LCB/build/lib" \
  -lcouchbase
```

Differences vs. the naive homebrew command, and why each matters:

| Flag | Why |
|------|-----|
| `-I $LCB/include` | libcouchbase public headers (`libcouchbase/couchbase.h`, `vbucket.h`) |
| `-I $LCB/build/generated` | `configuration.h` is **generated by CMake** into the build dir, not in `include/` |
| `-L $LCB/build/lib` | link against the freshly built dylib |
| `-Wl,-rpath,$LCB/build/lib` | dylib install name is `@rpath/libcouchbase.2.dylib`; the embedded rpath makes the binary load **your** lib at runtime instead of `/opt/homebrew`'s |

(Alternative to the rpath flag: prefix the run with
`DYLD_LIBRARY_PATH="$LCB/build/lib"`.)

## 3. Run

```bash
./prog_fixed
```

Most tests prompt for username/password on stdin. To script it:

```bash
printf 'couchbase\ncouchbase\n' | ./prog_fixed
```

Turn on full libcouchbase logging to see bootstrap endpoints, TLS, and config:

```bash
printf 'couchbase\ncouchbase\n' | LCB_LOGLEVEL=5 ./prog_fixed
```

## 4. Confirm you're on the right library

```bash
otool -L prog_fixed | grep -i couchbase      # should show @rpath/libcouchbase.2.dylib

# and at runtime the version line should be the bundled changeset, e.g.:
#   Version=3.3.19_5_g9f48bed987, Changeset=9f48bed987...
# NOT the homebrew build.
```

Expected healthy output for `0.connect_to_analytics_without_ssl.cpp` against a
cluster with analytics, bootstrapping on a management port with `=http`:

```
✅ Connected to Cluster!
  Analytics port (cbas): 9600      <- FOUND on each node
Result: {"$1":1}
✅ Query Completed.
```

If `cbas` shows `NOT FOUND` and the query returns
`LCB_ERR_UNSUPPORTED_OPERATION (214)`, you are almost certainly linked against
the stock homebrew lib — recheck steps 2 and 4.

## Toolchain used (macOS)

- Apple `g++` (`/usr/bin/g++`), C++17
- CMake ≥ 3.20 (`/opt/homebrew/bin/cmake`)
- OpenSSL 3 from Homebrew (`/opt/homebrew/opt/openssl@3`)
